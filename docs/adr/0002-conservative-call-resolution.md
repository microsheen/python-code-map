# ADR-0002: 保守的调用解析 —— 只连唯一确定的边，其余带 reason 归档

- 状态：已采纳（Accepted）
- 日期：2026-09
- 相关：ADR-0001（纯前端 + tree-sitter WASM，没有类型信息）

## 背景

ADR-0001 选定了 tree-sitter 做语法层解析，代价是**没有类型推断**：
看到 `obj.method()`，我们知道有个调用，但不知道 `obj` 是哪个类的实例。
再叠加 Python 本身的动态特性（`getattr`、鸭子类型、monkey patch、`*args` 转发、
把函数当值传递、闭包变量遮蔽同名函数），**完整的静态调用图是不可判定的**。

于是必须选一种"错法"。这里的关键判断是：

> 对一张给人读代码用的调用图来说，**一条错误的边比一条缺失的边糟糕得多**。

缺失的边最多让用户少看一条关系，而且如果缺失是可见的、可计数的，用户知道该去搜什么；
错误的边会让用户顺着它去读一段根本不会被执行的代码，并且**摧毁对整张图的信任** ——
一旦用户发现图骗过他一次，他就再也不信这张图了。

## 决策

**只连"唯一确定"的边。候选数为 0 或大于 1 时一律不连，但把调用点完整记录下来并给出 reason。**

实现集中在 `src/parser/resolveCalls.ts`。

### 解析顺序（`resolveSimpleName` / `resolveDottedName`）

对一个裸调用 `foo()`，按下列顺序找候选，命中唯一解就连边：

1. **局部作用域链**（当前函数帧 → 外层嵌套函数帧 → 模块帧）。
   如果 `foo` 已被局部变量/参数遮蔽，判 `dynamic` —— 静态无法确定那个变量装的是谁。
2. **本文件的模块级定义。** 同名定义多于一个（如条件分支里重定义）→ `ambiguous`。
3. **import 绑定表**（`src/parser/imports.ts`）。`from m import f` 之后裸调 `f()`，
   若 `m` 在上传集合里且 `f` 在 `m` 中唯一 → 连边。
4. **同模块内唯一同名定义**作为兜底（用户上传零散文件、没有完整包结构时仍能连上）。

对带接收者的调用：

- `self.foo()` / `cls.foo()` → 找**最近的 class 帧**，在其中找 `foo`；
  基类里也有同名方法时若无法唯一确定 → `ambiguous`。
- `Cls.foo()`（`Cls` 是本次收集到的类名）→ 解析为 `Cls.foo`；
  实例化 `Cls(...)` 会进一步指向 `__init__`（若存在且唯一）。
- `mod.foo()` / `pkg.mod.foo()` → `mod` 必须是 import 别名、指向已上传文件、
  且该文件中 `foo` 唯一，三个条件缺一不连。
- 其余接收者（普通变量、链式调用 `a.b().c()`、`getattr(o, "f")()`、lambda 调用、
  调用的目标是个模块对象本身）→ `dynamic`。

### reason 分类

所有没连上的调用点都进 `CallGraph.unresolved`，带四类 reason 之一：

| reason      | 含义                                             | 典型例子                                                              |
| ----------- | ------------------------------------------------ | --------------------------------------------------------------------- |
| `ambiguous` | 候选多于一个，静态无法判定是哪个                 | 同名函数在多处定义；`self.foo` 在多个基类中都有                       |
| `external`  | 目标不在上传集合内 —— Python 内置或第三方/标准库 | `print()`、`len()`、`open()`、`requests.get()`                        |
| `dynamic`   | 接收者/目标是运行期才确定的值                    | `getattr(o, "f")()`、`cb()`（`cb` 是参数）、`a.b().c()`、局部变量遮蔽 |
| `unknown`   | 这个名字在可见范围内找不到任何定义               | 拼错的函数名、只上传了调用方没上传被调方                              |

内置名单在 `src/parser/builtins.ts`；"import 的模块头不在索引里"同样判 `external`。

### 未连边的调用点不丢弃

这是本决策能成立的前提 —— 保守只有在"漏掉的东西看得见"时才不是偷懒：

- 按源函数聚合成 `unresolvedCount`，显示为**图节点右上角的角标**。
- 顶部工具栏给出全局 `byReason` 统计（四类各多少个）。
- `showExternal` 开关打开时，把所有 `external` 调用聚合成**一个**灰色合成节点
  （`EXTERNAL_NODE_ID = __external__::builtins`，标签 `builtins / 3rd-party`）。
  默认关闭，因为逐个展开内置调用会让节点数爆炸、把真正的业务关系淹没掉。
- 边是聚合的：同一对函数之间的多次调用合并成一条边，保留全部 `callSites`，
  `weight = callSites.length` 影响线宽。自环（递归）保留并标记 `selfLoop`。

## 备选方案与为什么不选

- **把 unresolved 也画成虚线边。** 直觉上"信息更全"，实测是噪声灾难：
  一个 `print()` 密集的脚本会让每个节点都连向一堆虚线，真正的调用关系被彻底淹没。
  折中方案是只把 `ambiguous` 画成虚线，但那需要一个"用户看得懂为什么这条边是虚的"的 UI，
  收益不抵复杂度 —— 改为用角标 + 统计来表达。
- **上类型推断（pyright/mypy 级别）。** 能显著提高召回率，但在浏览器里做不到：
  pyright 需要完整的模块解析与 stub 生态，Pyodide 方案见 ADR-0001 已被否。
- **按名字全局匹配（同名就连）。** 召回率最高、精度最低，正是上面说的"会骗人的图"。

## 后果

**正面**

- 图上每一条边都可信，且带 `CallSite`（file/line/column/text），可追溯。
- 漏连是**可见的**：角标 + byReason 统计 + `unresolved` 列表，用户知道该去搜什么。
- 解析规则是纯函数，可以逐条写单测（用例矩阵见 `__tests__/`），改规则时回归风险低。

**负面**

- **动态派发密集的代码会显得"边很少"。** 大量 `getattr`、依赖注入、回调注册表、
  策略字典的仓库，图上会是一堆孤立节点加高角标。这是有意的取舍，不是 bug；
  但需要在 UI 上诚实表达（角标就是为此存在的）。
- 用户上传**不完整的文件集合**时，跨文件的边会退化成 `unknown`。
  `src/parser/modules.ts` 的"按文件名尾段模糊匹配 import"兜底缓解了一部分，
  但根治办法只能是上传完整的包。
- 精度规则会持续需要调整，因此需要一个基线来防止无声漂移（见下）。

## 回归基线

`fixtures/` 三个文件（`main.py` / `shapes.py` / `utils.py`）的解析产物被写死为测试基线：

```
funcs = 45   edges = 47   unresolved = 28
byReason = { ambiguous: 1, external: 14, dynamic: 13, unknown: 0 }
```

**改动解析规则时如果这组数字变了，必须解释变化的来源**（哪条规则放宽/收紧了、
为什么这是对的），并同步更新基线，而不是顺手把测试改成新数字。
