# ADR-0005: 图上的一条线可以点 —— 聚合边的「第几处调用」循环定位

- 状态：已采纳（Accepted）
- 日期：2026-10-15
- 相关：ADR-0002（边是聚合的、`callSites` 全量保留 —— 本决策消费的就是那份数据）、ADR-0001（纯前端：点线不产生任何网络上行）

## 背景

提出来的需求有两条：

1. 可以点击调用关系图中的**线**，点下去定位到「A 调用 B」的那个位置；
2. A 可能调用 B 三次（真实仓库里可能是三十次、两百次），一根线对应 N 个位置，怎么办。

难点不在"线能不能点中"，而在**一条边不是一个位置**。ADR-0002 把同一对函数之间的所有调用
合并成一条边，`weight = callSites.length` 只影响线宽；在屏幕上它是一根折线、一个几何体，
背后却是 N 个 `(file, line, column, text)`。所以真正要回答的是：**空间上的一根线，怎么承载
时间上的 N 次跳转**，以及这三处入口（图上、代码区、底栏）怎么保证说的是同一个序号。

落地前必须一并考虑的现实约束：

- 平行边不能画。一个被调用两百次的 `logger.info()` 如果画成两百条线，dagre 的布局会退化
  成一团，"边 = 一对函数之间的关系"这个语义也当场没了。
- 边可能有一个端点被裁在当前范围之外（Neighborhood / This File 下仍有跨界边），
  所以端点标签要能从全量图回退取值。
- **一条边的全部 callSites 必然在同一个文件** —— caller 只可能在一个文件里定义，
  它的调用点自然都在那个文件。这是 `collectCalls` 给的不变量，代码区因此不需要跨文件分组。
- 线的可见宽度只有 2~3px，直接按几何命中的话鼠标要点得很准。

## 决策

### 1. 点线只"高亮这根线 + 定位调用点"，不动图的选中语义

`edgeSelection` 是与 `selection` 并列的独立状态（`src/state/store.ts`）。点线**不改**
`selection`、`scope`、`navHistory`、`view` —— 不居中、不平移、不裁剪邻域。否则每点一次线整张图
就重排一次，用户会立刻找不到自己刚才在看什么。被改的其它状态只有一个：`activeFile`，
因为定位的落点本来就在代码区。

### 2. "第几处"只有一个口径：`sortedCallSites`

`src/graph/edges.ts` 把边的调用点按**源码顺序**排：行号升序 → 同行按列升序 → 原文兜底。
图上显示的序号、代码区的打点编号、底栏那行文本，全部取自这个数组的下标。
任何地方都不许再 sort 一次，也不许依赖 buildGraph 的插入顺序 —— 否则三处 UI 会在同一份
数据上给出三个答案，而这类不一致是用户唯一会当成"图在骗我"的时刻。

同一个模块还提供 `edgeKey` / `splitEdgeKey`（`<source>-><target>` 的唯一拼法，与
`layout.ts`、`hooks.useNeighborEdgeIds` 同源）。

### 3. N 处调用：三个入口 + 一条循环规则

1. **重复点同一根线 = 往后循环**：1/3 → 2/3 → 3/3 → 1/3。**Shift + 点**反向。
   换一根线、或者清除之后再点，**一律从第 1 处开始**（包括 Shift 的那次首次点击 —— 反向
   这个语义只在"同一条边已经选中过"的前提里才成立，否则它只能意味着"从第 0 个往前减一"）。
2. **代码区右下角的步进器** `‹ k/N ›  ✕`：键盘式逐处前后走，绕回。N=1 时 `‹›` 不渲染
   （只有一个答案的时候不假装可以翻页），显示 `1/1`。
3. **N 处全部打点**：不是只显示当前那处。当前处加深 + 左侧竖条 + 序号角标，其余各处留一条
   下划线式淡标记。这样"这里一共调了几次、分别在哪几行"在一次点击之后就是**全部可见**的，
   循环只是在里面挑一个焦点。

浮层放右下角而不是弹列表，是因为它必须**常驻**：弹层要点别处就消失，而用户读代码时正需要
一直看得见"这是 3 处里的第 2 处"。

### 4. 命中：屏幕像素容差 + 节点优先

`EDGE_HIT_TOL = 7`，单位是**屏幕像素**（世界容差 = tolPx / scale），所以缩到 20% 时细线照样点得中，
放大时命中区也不会胖到抢走相邻的线。7px 大致等于箭头宽度。命中几何用的是 `layout` 里与
`d` 同源密采样的 `points`，保证"看到的线"和"点得中的线"不各自漂移。先判节点矩形、再判边
（节点面积大，边只吃剩下的空白）；多条边同时命中取最近的。拖动超过 `DRAG_SLOP = 4` 不算点击。
边数超过 `MAX_HOVER_EDGES = 1500` 时关掉 hover 命中（点击仍然可用）—— 鼠标每动一下全量扫描太贵。

### 5. hover：手型 + 一句提示，不带任何副作用

线上手型光标，旁边出 `A → B · N call sites · first at line L`（N=1 时是 `A → B · line L`）。
实现是原生 `pointermove` + rAF 节流，光标用命令式 `el.style.cursor` 改写 —— 不为一个手指形状
把整棵树重渲染。tooltip 位置累计位移超过 `HOVER_MOVE_SLOP` 才更新，否则同一条边上每动一像素
都要重排一次。

### 6. 反向：代码 → 边

点代码里的调用 token 时，除了选中被调函数（原有语义），还把 `origin='code'` 的边选中设上，
图上那根线随之加粗高亮。`origin` 唯一的作用是决定代码区要不要滚动 + 闪烁：
从图上来（`graph`）要，因为用户需要看见落点；从代码里点（`code`）不要，因为用户已经在那一行了，
再闪一次是打扰。

### 7. 什么时候清除

点节点、点图上的空白、步进器 `✕`、切范围、后退/前进、重新上传、清空 —— 都清除边选中。
在同一条边上循环点击**不**清除。边选中不参与 `navHistory`（那是函数级历史，边是函数之间的关系）。

## 这套功能的硬不变量

1. 点线 / 循环 / 步进 / hover 全程**零网络上行**（冒烟 I8 钉住）。
2. 点线**不改** `selection` / `scope` / `navHistory` / `view`（appFlow 用引用相等断言 view 没动）。
3. 一条边的全部 callSites 同文件（`collectCalls` 保证，代码区据此不分页）。
4. "第几处"只由 `compareCallSites` 决定，别处不得自行排序。

## 备选方案与为什么不选

- **把 N 次调用画成 N 条平行边。** 最直接地回答"三次调用怎么定位"，但直接和 ADR-0002 的
  骨架冲突：边数放大 N 倍、布局崩、一对函数不再是一条关系。否。
- **点线弹出一个调用点列表让你挑。** 多一步、要多一套焦点与定位管理、会遮挡图，且关掉就没了。
  现在的"全部打点 + 常驻步进器"表达的其实是同一份信息，不需要临时弹层。
- **只跳第一个调用点，剩下的让用户自己去搜。** N>1 时用户点第二次会以为功能坏了。
- **在每条线上打 ①②③ 序号标签。** 折线沿线放 N 个文本要处理遮挡与缩放，密集图上一定糊。
- **hover 时只高亮这条边的某一段路径。** 数据上根本不存在"某一段"：一条边只有一个几何体。

最终选择可以概括成一句话：**一根线保持一根线，把 N 次调用放到时间维度上循环，同时用
"N 处全打点"把空间分布一次性摊开。**

## 后果

**正面**

- 一条边背后的 N 次调用不再是黑盒：点一次知道有几处，且每处都能走到。
- 图上点线不会引起重排，可以连续点着读代码。
- 序号只有一个来源，三处 UI 不可能打架。

**代价与后续**

- **N 很大时循环点击不现实。** 两百处调用要按两百次。真正的出路是一个"调用点列表"面板
  （文件 + 行 + 代码片段，可直接跳），那需要新的布局预算。这一轮先不做：把 3 处、5 处这类
  常见情况做顺，比给 200 处做一个同样难受的列表更有价值。
- 点线不居中不改范围是刻意的，代价是当落点在别的文件、而图仍显示原范围时，用户得自己回到
  那根线。后续可以做的是"点线后把那根线的两个端点在图上标出来"，但仍然不重排。
- **未解析的调用不参与点线**（`ambiguous` / `dynamic` 按 ADR-0002 根本没有边）。
  图上点不到的地方不代表没有调用，这件事仍由节点角标与 byReason 统计表达。

## 这三处是真的实测过（证据）

- **jsdom 端到端**：`__tests__/appFlow.test.tsx`「验收 3：点调用关系图的线 → 定位到 A 调用 B
  的那一行」10 条 —— 含连点四次 `1/3→2/3→3/3→1/3`、Shift 反向、点节点/点空白清除、
  线上拖动只平移（`view.tx` 变了但没触发点线）、从代码点调用点不闪烁。
- **真浏览器**：`scripts/browser-verify.mjs` I 组 15 条。折线的屏幕坐标由
  `getPointAtLength + getScreenCTM` 手算，再用 `elementFromPoint` 确认命中的确实是这根
  `<g data-testid="graph-edge-...">`；三个打点的 `left` 严格递增，正是调用列 12 < 13 < 19 的
  可见证据；整个 I 组跑完 `netRequests` 一条都不多。
- **单元**：`__tests__/edges.test.ts`（口径与 key 编解码）、`__tests__/store.test.ts`
  （循环 / 越界 / origin / 清除）、`__tests__/graphPaneMath.test.ts`（容差换算、节点优先）。
