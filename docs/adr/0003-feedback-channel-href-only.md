# ADR-0003: 反馈渠道只长成两枚 href —— 白名单计数诊断 + 门控别名

- 状态：已采纳（Accepted）
- 日期：2026-10-15
- 相关：ADR-0001（纯前端、没有服务端存储；本决策是那条承诺在「往外搬信息」这件事上的延伸）

## 背景

反馈是整个站点里**唯一一个天生要把信息往外搬**的功能。前面所有承诺说的都是
「你的源码不出这台机器」，而反馈存在的目的恰好相反 —— 所以它是那份承诺最容易被打穿的口子：
一个「顺手加的自动上报」就能让整份承诺变成措辞游戏。

三条既有约束决定了这里没有自由发挥的余地：

1. **没有后端**（ADR-0001），托管是 Direct Upload 的纯文件站点，服务器物理上没有写的能力
   （ops §1 第三条）。于是「提交到服务端」这条路根本不存在，不是被禁用，是没有。
2. **CSP 是 `default-src 'none'` 起手**，只放开 `wasm-unsafe-eval`，没有 `connect-src`、
   `form-action` 是 `'none'`（ops §4/§5）。页面里真去 fetch 会当场被 CSP 打死并冒烟可见。
3. **仓库与站点都是公开的**：任何写进代码或页面的联系方式都会被爬；而任何「自由格式的诊断字段」迟早会把用户的文件名、函数名甚至代码原文搬出去。

还有一条来自隔壁项目 Event_Logger 的实测教训：诊断文本只要**允许**一个未经收口的字段，
它在某个版本里就会带上用户内容 —— 靠人 review 住不住。

## 决策

### 1. 对外动作只能是两枚由用户点击的 `<a href>`

- **GitHub Issues**（公开、可跟进、别人能看到同一个问题的其它报告）为主渠道；
- **mailto 别名**（私密、无跟踪）为次要渠道，且由常量门控（见决策 4）；
- 面板里不出现任何自动请求：没有 `fetch` / `XMLHttpRequest` / `sendBeacon` / `new Image(` /
  `<form>` / `window.open` / `WebSocket` / `EventSource` / `document.cookie`。
  这些不是「代码风格约定」，而是 `scripts/audit-egress.mjs` 逐字读的**文本判据**（注释也算）。

连「复制诊断到剪贴板」这个看起来很无害的按钮也**不做**：`navigator.clipboard.writeText` 是这条
路上唯一会被承诺掉的出口能力，一旦有它，「页面自己发不出任何东西」这句话就要加限定语。
替代方案是地址块用 `user-select: all`，用户三击就选中，复制与否由操作系统决定。

### 2. 诊断是**白名单 + 只计数**，不是黑名单

`src/feedback/contact.ts` 冻结了一份有序 8 字段：
`build, ua, files, funcs, edges, unresolved, warnings, persisted`。

- 黑名单的失败模式是「新字段忘了排除」，泄漏发生在没人看的地方；
  白名单的失败模式是「新字段没加进去」，表现是多一个 `unknown`，**看得见**。
  一个只会少说、不会多说的收口，才是可以长期依赖的收口。
- 数值字段一律 `toCount`：数组取 `.length`，有限数字取整并夹到 `>= 0`，
  **其它一切退化为 0，绝不 `String(x)`** —— 后者等于把调用方塞进来的任何东西原样搬进对外文本。
- 布尔字段 `toYesNo` 是三态：`true`/`yes` → `yes`，`false`/`no` → `no`，其余一律 `unknown`。
  刻意不做强制转换：`'true'`（字符串）这种脏值如果悄悄变成 `yes`，
  就再也看不见「调用方写错了」这个信号。
- 换行与控制字符按码点剥掉：诊断块是逐行 `key=value`，混进一个换行就伪造出一行假字段。
- 长度有预算（总长 600、`ua` 160、标量 64），超预算只截 `ua` 的尾巴，**绝不整行丢弃**。

### 3. `build` 在运行时取，且只取哈希前 8 位

- 从正在执行的那枚 `<script src=".../entry-<hex>.js">` 里读，而不是写死常量：
  写死等于把「反馈说的是你看到的那批字节」换成「发版时记得改」，而人会忘。
- 只取前 8 位：完整 32 位十六进制长得像 token，公开仓库审计会按疑似凭据报警（ops §4 有这条戒）。
- 取不到就诚实返回 `unknown`（`npm run web` 的 Metro dev bundle 不匹配那个形状，属预期）。

### 4. 邮件别名是一个常量门，默认关闭

`CONTACT_EMAIL: string | null = null`。关闭时 `mailtoUrl()` 返回 `null`，面板不渲染地址块、
不渲染邮件链接、也不渲染「没有邮件客户端怎么办」的提示 —— DOM 里连一个 `@` 都没有。

- 为什么代码先行、路由后开：Email Routing 尚未开通，本机也没有 Cloudflare 凭据（ops §10）。
  在「文档里打算用」和「页面上有一个真能收到信的地址」之间，隔着一次**实际发出的测试信**。
  先上线一个收不到信的地址，比先上线一条渠道更糟。
- 启用是**一个常量 + 同一个提交里的 `--public-address=`**：分两个提交做，
  要么扫描器红（源码里出现未公开的地址），要么留下一个没人认领的地址。
- 转发目标邮箱**永不**进仓库、git 历史、文档；映射只存在于控制台 Destination 字段（ops §9）。

### 5. 面板是只读入口，故意不被 `busy` 门控

解析中、以及从 IndexedDB 恢复出旧会话时，反馈按钮都必须能点。盯着那份恢复出来的旧版本看的人，
正是最需要报 bug 的人。这个「不 gate」是有意的，源码里留了注释防止下一次重构顺手「修好」它。

## 备选方案与为什么不选

- **自建后端 / Cloudflare Function 收 POST。** 直接推翻 ADR-0001 与「服务器没有写能力」这条
  最硬的承诺；为了收反馈而引入一个能写用户数据的组件，代价和收益不成比例。
- **第三方表单（Google Form / 问卷 / 反馈平台）。** 那是把用户内容交给一个我们无法用 CSP 约束、
  也无法用冒烟审计的第三方 —— 等于在承诺面上开一个官方后门。
- **只留 GitHub Issues**（本仓 2026-10-13 的旧结论）。被用户于 2026-10-14 推翻：
  有些问题（带敏感路径的复现步骤、内部代码片段）不该被迫公开。代价记下来：
  多一条渠道就多一个公开联系地址与一份垃圾邮件面，所以才要有门控常量与 ops §9 的启用 runbook。
- **黑名单式诊断（排除文件名，留下自由文本）。** 见决策 2：失败模式发生在看不见的地方。
- **诊断全量 JSON 上报。** 定位能力更强，但它需要一条真正的上报通道 —— 那正是本决策要否掉的东西。

## 后果

**正面**

- 「打开反馈面板不会发出任何东西」是可证的，而且已经被证了三遍：静态扫描 + jest 金丝雀 +
  真浏览器冒烟 G2（开→关整个来回，请求集一个都没多）。
- 用户改过的诊断文本会同时进两枚链接，「你点出去的就是框里那些字」成立。
- 门控关闭期间源码里零邮箱字面量，公开仓库审计（含 `--history`）没有新面要扫。

**负面**

- 邮件**没有送达保证**：只开 Routing 不开 Sending，没有 SPF/DKIM/退信处理，
  信件可能被判垃圾。这也是把 Issues 定为主渠道、并在面板里写明「回信来自个人邮箱」的原因。
- 只有计数的诊断比原始日志更难定位问题。换来的是「没有任何一条路径能把代码搬出去」，
  维护者需要在 Issue 里多问几句才能拿到复现细节 —— 这是买断承诺面所付的代价。
- 门控关闭期间面板只有一条渠道，想私密反馈的用户暂时只能开 Issue 自己删内容。
- 契约变多变硬：8 字段名单、11 个 `data-testid` 锚点、两枚链接的形状，同时被 jest、
  冒烟 G 组和 README 钉住，改一处要同步三处（冒烟 G 组直接把源码里的常量读回来比对，
  就是为了不让「冒烟还绿着但测的已经不是源码」发生）。

## 这三道闸门是真的在拦（证据）

| 闸门         | 位置                                                   |
| ------------ | ------------------------------------------------------ |
| 静态扫描     | `npm run audit:egress`，CI `checks` 里的 blocking 步骤 |
| jest 金丝雀  | `__tests__/feedback.test.tsx`                          |
| 真浏览器冒烟 | `scripts/browser-verify.mjs` G1–G6，排在 E 组之前      |

- **静态扫描**：三个受审文件里出现任何请求原语或未公开的邮箱字面量就红，**注释里也算**
  （扫描器是纯文本匹配，它不认识语法，所以注释也拦）。
- **jest 金丝雀**：把显眼秘密喂进诊断来源，断言它们在诊断文本、Issues href、mailto href
  三种输出里一个都不出现，且输出里不长出 `name=` / `path=` 这类字段痕迹。
- **真浏览器冒烟**：面板真的出现、开→关整个来回请求集一个都没多、恰好 8 行且第 i 行是第 i 个
  字段、`build` 等于被测那批字节的哈希前 8 位、计数与页面上真实渲染的数字自洽、
  `<a>` 数与门控一致、零 `<li>`，以及面板**浮在最上面**。

第三道闸门上线当轮就抓到过一个只有真浏览器能发现的问题：面板在 DOM 里、`getBoundingClientRect`
坐标正确、诊断文本也对，但截图里根本看不见，点「关闭」点到了图上。原因是 react-native-web 的
`View` 基础样式写死 `position: relative` + `zIndex: 0`，于是**每一个 View 都是一个层叠上下文**，
遮罩的 `z-index: 1000` 只在顶栏那一层内部比大小，整体仍排在正文面板之后（`elementFromPoint`
在面板中心返回的是 `svg#graph-svg`）。修法是把顶栏自己的 `zIndex` 放开为 `auto`
（`src/components/TopBar.tsx` 里有整段注释），并把「关闭按钮中心的命中测试」写进 G6 作为断言。

jsdom 永远发现不了这件事 —— 它没有布局。这正是「承诺由闸门把守、而不是由 review 自觉」的论据。

## 回归基线

```
诊断字段（顺序即契约）= build, ua, files, funcs, edges, unresolved, warnings, persisted
长度上限               = 总 600 / ua 160 / 标量 64
面板锚点               = 11 个 data-testid（门控开启时全部渲染；关闭时 7 个）
链接数                 = CONTACT_EMAIL === null ? 1 : 2
冒烟断言总数           = 47（41 + G1–G6）；请求集仍是 9 个，全同源、全 GET、零请求体
jest                   = 17 suites / 280 tests（feedback.test.tsx 27 例）
```

改这些数字中的任何一个，必须同时改 `contact.ts`、`FeedbackDialog.tsx`、
`__tests__/feedback.test.tsx`、`scripts/browser-verify.mjs` 的 G 组与 README ——
冒烟脚本会读源码常量做比对，改了源码不改断言（或反之）都会红。
